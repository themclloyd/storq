# StockWise POS

I have an application idea to help business owners who run a single store or multiple stores track their stock and sales and perform stock taking with their staff. I want a single email and password that can be used on different devices, whether for a cashier or the owner, separated by a four‑digit PIN. Each cashier or admin would have their own PIN, which indicates their role. Because in Africa it’s hard for everyone to have an address, the company can use a cell phone or laptop to log in the user and enter their PIN. There are no contradictions in how this will work. That's what I want. also support layby. lastly lets have two type of stores direct sale a normal one and second one can be approved based system where a cashier will create invoice and other user will be able to approvae that invoice but i realy want that both must work based on its type.

## Generated files & codegen boundary

The app is a normal Git repository with a real build (Vite + TanStack Start → Cloudflare Workers), so it is fully exportable and can be developed without Lovable. A handful of files, however, are **regenerated by tooling and must not be hand-edited** — edit the source of truth instead:

| Path                                                                                 | Owned by                 | Regenerate with                                        |
| ------------------------------------------------------------------------------------ | ------------------------ | ------------------------------------------------------ |
| `src/integrations/supabase/{client.ts,client.server.ts,auth-middleware.ts,types.ts}` | Lovable Cloud / Supabase | Reconnect Supabase in Lovable, or `supabase gen types` |
| `src/routeTree.gen.ts`                                                               | TanStack Router          | Auto on `bun run dev` / `build`                        |
| `.qoder/repowiki/**`                                                                 | IDE knowledge index      | Tool-managed; ignore                                   |
| `bun.lock`                                                                           | Bun                      | `bun install`                                          |

Everything under `src/lib`, `src/components`, `src/routes` and `supabase/migrations` is hand-written application code and safe to edit directly. Business rules that must stay authoritative live in SQL (`supabase/migrations`) — the Lovable/Supabase layer only wraps them.

## Supply-chain & quality gates

- **`bunfig.toml`** enforces a 24h minimum-release-age guard so freshly published (and potentially malicious) package versions are never auto-installed.
- **`package.json > overrides`** pins known-vulnerable transitive build deps (js-yaml, nanoid, source-map-js) to patched releases; keep these until upstream majors ship fixes and verify with `bun audit --production`.
- **CI** ([`.github/workflows/ci.yml`](.github/workflows/ci.yml)) gates every push/PR on `bun audit --production`, `bun run lint`, `bun run format:check`, `bun run test` and a real `bun run build` — the guard against one screen's fix silently breaking another.
