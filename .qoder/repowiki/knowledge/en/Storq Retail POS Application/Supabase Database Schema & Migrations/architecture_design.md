The module is a flat collection of timestamped SQL migration files under `supabase/migrations/`, driven by the Supabase CLI against project `gtkfczmudhzhbdooftsa` (declared in `config.toml`).

- Data model: multi-tenant retail schema with `businesses` as the tenancy root, then `stores`, `staff`, `products`, `store_stock`, `sales`, `sale_items`, `payments`, `stock_takes` / `stock_take_lines`, plus later additions for refunds, expenses, cash shifts/movements, collections/product_collections, subscription billing, and PIN brute-force throttling.
- Security boundary: RLS is enabled on every table; authenticated clients get SELECT only, while all writes go through `SECURITY DEFINER` functions. The `public` schema exposes thin `public.*` wrappers that delegate to `app.*` implementations, which are the real business logic. Internal helpers (`require_staff`, `pin_taken`, `_move_stock`, `effective_price`, `subscription_active`) are revoked from `public, anon, authenticated` and kept service-role-only.
- Tenancy enforcement: `public.my_business_id()` resolves the current user's business from `auth.users`; later hardening adds `app.session_role()` bound to a device-scoped staff session (`staff_sessions.auth_uid = auth.uid()`) so money-sensitive reads require a verified PIN unlock.
- RPC surface: every client-facing mutation is a function taking a UUID staff token plus parameters; role checks are done inside `require_staff` against arrays like `['admin','manager','cashier']`. Business rules (PIN shape, price bounds, stock floors, plan limits) live in both CHECK constraints and PL/pgSQL validation.
- Migration ordering: initial schema + RLS in the first file, indexes in a dedicated index migration, security hardening in `20261008090000_security_hardening.sql` (which rewrites most `public.*` functions into `app.*`), then feature migrations for retail operations, sales summaries, item codes, and fixes.
