# Project rules

- Enforce paid store capacity and expiry in SQL; confirmed payment snapshots grant capacity, and store creation serializes on the subscription row. Why: clients and concurrent requests cannot create unpaid stores.
- Price every payment on the slots it actually buys (`subscription_payments.billed_stores`): an active subscription raising its slot count pays for the new slots only and keeps the expiry it already bought, while renewals and reactivations bill all slots and extend the term. Activation stays service-role-only and idempotent. Why: adding a location must neither re-charge an already-paid store nor silently shorten prepaid time.
- Keep workspace navigation policy in a client-safe shared module and group existing URLs with shell-level page tabs; filter by the signed-in person's access grants and selected store type. Why: fewer sidebar entries without broken deep links or lost staff tools.
- Define workspace theme tokens once for `.storq-workspace` and `body:has(.storq-workspace)` so portaled dialogs inherit the same theme; leave public pages independent. Why: operations and their overlays stay consistent without changing public marketing or shared collections.
- Loading is a skeleton of the screen it becomes, never a centred "Loading…" line: a query in flight renders the header, KPI tiles, table columns or card rows it will fill, using the shared placeholders in `src/components/pos/skeletons.tsx` (`TableSkeleton`, `ListSkeleton`, `RowsSkeleton`, `StatSkeleton`, `TileSkeleton`, `PanelSkeleton`, `DetailSkeleton`) and `Stat`'s `loading` prop so a figure is held rather than printed as zero. A screen that already shows data swaps values in place and never flashes a skeleton over them. Why: a slow read must not pass for an empty shop or a real zero, and the layout keeps its shape instead of collapsing and reflowing.
- All writes go through Postgres SECURITY DEFINER RPCs that take a staff session token (`p_token`) and check the capability they need via `app.require_perm(p_token, permissions)`; tables are read-only via RLS. Why: one shared business login per device, so access must be verified server-side from the PIN session, not the client.
- A business has exactly one owner (`staff.is_owner`, created by `setup_business`); every other staff row carries a `permissions` checklist. Each area has two grants — `view_*` (read a screen and its numbers) and its change grant (`sell`, `stock`, `approvals`, `money`, `staff`, `locations`), where change implies view. Lists are stored compacted (`app.compact_perms`) and compared expanded (`app.expand_perms`), so a holder of a change grant may also hand out its view. `staff.role` is only the derived read tier for RLS. Why: the owner grants areas of the product, and a till-only person must not reach the catalogue by calling an RPC directly; a view-only person still needs `manager`-tier reads for costs, refunds and the ledger.
- Page gates use the shared `can(...)` helper with area pairs: `can("stock", "view_stock")` admits either grant and renders a read-only screen, `can("stock")` alone unlocks the write affordances. Why: navigation, screens and RPCs must agree on one meaning of access, so a viewer never sees a button the database will refuse.
- PIN hashes never leave the database: `public.staff` is granted column-by-column to `authenticated` and `pin_hash` is excluded, so the roster read cannot be cracked offline into an unlock as someone else. PIN verification and every override check stay inside `SECURITY DEFINER` functions; a table-level `GRANT SELECT` on `staff` would reopen the hole. Why: a readable bcrypt hash of a 4-digit PIN is an offline crack away from that person's screens.
- Business logic for store types (direct vs approval), layby and stock movement lives in SQL functions (`checkout`, `review_invoice`, `layby_pay`, etc.). Why: keeps stock and payments consistent across devices.
- Shared data hooks live in `src/lib/` (pos.tsx context, products.ts, sales.ts), never exported from route files. Why: route modules are code-split.
- Stock quantity changes must go through SQL paths that set a reason (`app.set_ctx`); a trigger on `store_stock` writes the immutable `stock_movements` ledger. Why: every unit of stock must be traceable.
- Refunds live in `refunds`/`refund_items` (never negative payments) and reports subtract them; cash drawer expected cash is computed server-side by `app.shift_summary`. Why: one consistent source for revenue and till variance.
- Documents (receipts, invoices, reports) are generated client-side as real PDFs via the shared builder in `src/lib/pdf.ts` (jsPDF, lazy-loaded); CSV import/export helpers live there too. Why: one consistent branded document style and no print-screen/HTML-popup output.
- Read-path budget: the till keeps one lean cached catalog (explicit columns, long staleTime) for instant scan/search; buying costs load only on screens that show them; freshness comes from targeted invalidation, polling only on live screens. Why: fast tills and low database load per tenant.
- Offline sales: direct-store sales queue in localStorage per account and replay through `checkout_ref` with a client-generated reference (unique on `sales.client_ref`); the instant-start snapshot persists only role-neutral reference data and is wiped on sign-out. Why: tills keep selling through outages without double-recording or leaking gated data.
- PIN lock/unlock drops only role-scoped queries (`isRoleScoped` in `src/lib/offline.ts`); shared reference data and the subscription entitlement stay cached and persisted, and the shell blocks on subscription only when no cached row exists. Why: instant till unlock and offline boot, while SQL remains the real subscription guard.
- Platform operators are a second principal: `require_platform_admin` resolves the JWT subject against `platform_admins`, and every cross-tenant write goes through an `ops_*` RPC that journals a typed reason. No impersonation path exists anywhere — staff authority only ever comes from a PIN session. Why: an operator must be able to fix a tenant's entitlement without ever reading or trading as them.
- Suspension and closure are their own clocks on `subscriptions` (`suspended_at`/`closed_at`) that gate `subscription_active()`; they never fake a `paid_until`, closure outranks suspension, and only a confirmed payment or `restore` lifts a suspension. Hard delete is `ops_purge_tenant` only (super admin, closed, 30 days after closure, name retyped) and writes a `platform_deleted_tenants` row that the business-creation trigger uses to deny a second free trial. Why: prepaid time stays intact, ending a business stays reversible for a month, and re-registering cannot farm trials.
- The Windows app in `storqdesktop/` is the same frontend built by `vite.config.desktop.ts`, never a second UI: one app, one set of screens, so a fix reaches the installer too. Its three target differences are hash routing (static files cannot answer a deep-link reload), `@/lib/billing.functions` swapped for `@/lib/billing.desktop.ts` (a packaged app has no server to run server functions), and `src/routes/shell.tsx` as the prerendered blank page the window opens on. Why: without the swap the installer ships server-function stubs that POST to a route that does not exist, and without the blank shell the marketing page flashes before the workspace.
- The installed app mirrors, it does not decide: localStorage stays the hot store and SQLite (`storqdesktop/src-tauri/src/db.rs`) is the durable copy of the same reference snapshot and the unsent-sale outbox, restored before the first query runs. Anything role-gated, any stock or price, and every activation still comes from Postgres. Why: a webview profile can be reset or "cleared", and money already taken at the counter must survive that without granting a device authority it never had.
- Desktop billing calls the deployed web API (`/api/desktop/config`, `/api/desktop/verify`) with CORS limited to the app's own origins, and those endpoints make the same PayChangu confirmation decision as the server functions. Why: the installer must be able to pay without shipping the secret key, and the two paths must never disagree about what counts as paid.
- The Windows installer is Authenticode-signed by `bun run tauri:build` → `storqdesktop/build-windows.ps1` → `sign-windows.ps1`, which resolves the machine's certificate and writes a generated, git-ignored `src-tauri/tauri.sign.json` that is merged as the last `--config`. A machine with no certificate builds unsigned and says so; a build that used one fails unless the finished installer verifies as valid _and_ timestamped. Why: SmartScreen shows "Unknown publisher" for anything it cannot attribute, a thumbprint is one store's fact and not the repository's, and an untimestamped signature dies with the certificate and takes the shop's trust with it.
