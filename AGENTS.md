# Project rules

- Enforce paid store capacity and expiry in SQL; confirmed payment snapshots grant capacity, and store creation serializes on the subscription row. Why: clients and concurrent requests cannot create unpaid stores.
- Price every payment on the slots it actually buys (`subscription_payments.billed_stores`): an active subscription raising its slot count pays for the new slots only and keeps the expiry it already bought, while renewals and reactivations bill all slots and extend the term. Activation stays service-role-only and idempotent. Why: adding a location must neither re-charge an already-paid store nor silently shorten prepaid time.
- Keep workspace navigation policy in a client-safe shared module and group existing URLs with shell-level page tabs; filter by staff role and selected store type. Why: fewer sidebar entries without broken deep links or lost staff tools.
- Define workspace theme tokens once for `.storq-workspace` and `body:has(.storq-workspace)` so portaled dialogs inherit the same theme; leave public pages independent. Why: operations and their overlays stay consistent without changing public marketing or shared collections.
- All writes go through Postgres SECURITY DEFINER RPCs that take a staff session token (`p_token`) and check role via `require_staff`; tables are read-only via RLS. Why: one shared business login per device, so staff role must be verified server-side from the PIN session, not the client.
- Business logic for store types (direct vs approval), layby and stock movement lives in SQL functions (`checkout`, `review_invoice`, `layby_pay`, etc.). Why: keeps stock and payments consistent across devices.
- Shared data hooks live in `src/lib/` (pos.tsx context, products.ts, sales.ts), never exported from route files. Why: route modules are code-split.
- Stock quantity changes must go through SQL paths that set a reason (`app.set_ctx`); a trigger on `store_stock` writes the immutable `stock_movements` ledger. Why: every unit of stock must be traceable.
- Refunds live in `refunds`/`refund_items` (never negative payments) and reports subtract them; cash drawer expected cash is computed server-side by `app.shift_summary`. Why: one consistent source for revenue and till variance.
- Documents (receipts, invoices, reports) are generated client-side as real PDFs via the shared builder in `src/lib/pdf.ts` (jsPDF, lazy-loaded); CSV import/export helpers live there too. Why: one consistent branded document style and no print-screen/HTML-popup output.
- Read-path budget: the till keeps one lean cached catalog (explicit columns, long staleTime) for instant scan/search; buying costs load only on screens that show them; freshness comes from targeted invalidation, polling only on live screens. Why: fast tills and low database load per tenant.
- Offline sales: direct-store sales queue in localStorage per account and replay through `checkout_ref` with a client-generated reference (unique on `sales.client_ref`); the instant-start snapshot persists only role-neutral reference data and is wiped on sign-out. Why: tills keep selling through outages without double-recording or leaking gated data.
- PIN lock/unlock drops only role-scoped queries (`isRoleScoped` in `src/lib/offline.ts`); shared reference data and the subscription entitlement stay cached and persisted, and the shell blocks on subscription only when no cached row exists. Why: instant till unlock and offline boot, while SQL remains the real subscription guard.
- Platform operators are a second principal: `require_platform_admin` resolves the JWT subject against `platform_admins`, and every cross-tenant write goes through an `ops_*` RPC that journals a typed reason. No impersonation path exists anywhere — staff authority only ever comes from a PIN session. Why: an operator must be able to fix a tenant's entitlement without ever reading or trading as them.
- Suspension and closure are their own clocks on `subscriptions` (`suspended_at`/`closed_at`) that gate `subscription_active()`; they never fake a `paid_until`, closure outranks suspension, and only a confirmed payment or `restore` lifts a suspension. Hard delete is `ops_purge_tenant` only (super admin, closed, 30 days after closure, name retyped) and writes a `platform_deleted_tenants` row that the business-creation trigger uses to deny a second free trial. Why: prepaid time stays intact, ending a business stays reversible for a month, and re-registering cannot farm trials.
